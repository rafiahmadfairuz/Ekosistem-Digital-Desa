## Implemented access boundaries

- Roles seeded include the nine project roles, including Village Head as role 9.
- Super Admin can manage technical accounts and region assignments but cannot assign Super Admin or Village Head through the UI and gains no official signing authority.
- RT/RW resident access requires a matching active assignment and region verification; officer screens expose only name and region.
- Residents can only edit their linked profile. BUMDes Managers can manage staff data without changing roles or gaining official approval authority.
- Phase 2 does not implement correspondence, internet/Wi-Fi, marketplace, payments, or signing modules.
- Region data supports multiple RW records per village and multiple RT children per RW. RT resident scope and RW officer scope follow the RT parent link; codes are unique per village for RW and per parent RW for RT.
- Village CRUD is available to Super Admin and Village Admin. Village Admin is scoped to the sole active village because no village-admin assignment table exists; Super Admin remains responsible for creating village records and editing RW/RT structure. Deletion is blocked while the village has any regions, and create/update/delete actions are audit logged.
- Super Admin can delete RT and RW records from the hierarchy view when they have no resident profiles or child regions. Assignment history is retained with former region snapshots and detached from deleted regions. Region deletion is audited. Migration `2026_11_09_000005_preserve_region_assignment_on_region_deletion.php` must be applied to MySQL before this behavior is available there.
- Added a dedicated `Pengaturan desa` page for village edit/delete and the RT/RW maintenance tree; the former `Data desa, RW, dan RT` page now focuses on creating the hierarchy. Super Admin and Village Admin can reach the settings page within their existing village-management scope.
- Hierarchy selectors, approval displays, resident region views, and dashboard assignment labels show RT/RW pairs without duplicate code/name prefixes. Admin hierarchy views show actual RW and RT counts per village. Regression coverage verifies RT code reuse across RW parents while blocking duplicates within one RW and duplicate RW codes within one village.
- Super Admin can permanently delete eligible accounts from `Akun dan peran`. Self-deletion and Super Admin/Village Head deletion are blocked; resident profiles without correspondence history are deleted with the account, while profiles tied to letters and BUMDes staff records require disabling the account. Region assignment rows are retained and detached from deleted users with a numeric former-user reference. Deletions are audited without recording personal contact data. Focused SQLite deletion tests pass. The related MySQL migrations still require application in the local database.
- Account status distinguishes pending activation, temporary suspension, and disablement. Suspension blocks access and revokes database sessions while retaining regional assignments; disablement also ends active RT/RW assignments. Reactivation after suspension restores access with existing assignments, while reactivation after disablement requires fresh assignments. Pending accounts can only be activated through the verified activation flow. Three focused SQLite lifecycle tests pass.
