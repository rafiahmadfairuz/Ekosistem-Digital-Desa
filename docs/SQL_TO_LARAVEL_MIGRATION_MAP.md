# SQL-to-Laravel migration map

Status: the inventory below covers all 36 SQL tables. The current implementation converts the identity/master-data foundation (`users`, `villages`, `roles`, `user_roles`, `regions`, `residents`, `region_officers`, and `bumdes_staff`) into one forward migration and Eloquent models. Correspondence, internet/Wi-Fi, marketplace/finance, and operational tables remain mapped here and are not yet migrated. No SQL was executed. MySQL 8 migration verification is pending because an accessible MySQL 8 server is not available in this environment.

Source file: `integrated_village_platform_mysql8.sql` (the requested filename with `(2)` is not present in this checkout).
Target: MySQL 8.0+, as declared in the SQL header. Runtime target must be verified on a disposable test database before claiming migration compatibility.

The source defines 36 tables. The mapping below preserves each column declaration and all table-level indexes, unique keys, checks, and foreign keys. Laravel migrations will use schema-builder methods and explicit constraints; the SQL `CREATE DATABASE`, `USE`, `SET FOREIGN_KEY_CHECKS`, and role `INSERT` statements are not to be copied or executed.

## Laravel conversion decisions

- Use ordered migrations for the five groups above, then create foreign keys only after all referenced tables exist. Keep SQL names, nullability, unsignedness, precision, JSON, enum values, defaults, indexes, checks, and delete actions unless a documented compatibility issue requires a team-approved change.
- Use Laravel `$table->id()` for `BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`; use `decimal(14, 2)` for money; use JSON columns for the source JSON fields; keep `VARBINARY(16)` IP values binary or document a safe portable representation.
- Convert each SQL `ENUM` to a documented Laravel/PHP backed enum or a database enum only after checking the supported database engine. MySQL 8 is the declared target; no MariaDB equivalence is assumed.
- Preserve unique/check/index definitions, including the exact-one-target check on `payments`, non-negative price/stock/amount checks, positive quantities, payment target FKs, and restrictive deletion for review, document, payment, order, and audit history.
- `assisted_service_sessions.reference_type/reference_id` and `notifications.reference_type/reference_id` are polymorphic pairs without native foreign keys; validate their targets and authorize access in application code.
- Seed only the role reference rows idempotently. The source SQL’s `ON DUPLICATE KEY UPDATE ... VALUES()` is replaced by Laravel `upsert`/`updateOrCreate`; no real village, official, resident, seller, or credential is seeded.

## Phase 2 schema additions

- `audit_logs` is present in the SQL source and is added as a native Laravel migration in Phase 2 with the source indexes, nullable user foreign key, JSON metadata, and binary IP storage.
- `residents.region_verified_at TIMESTAMP NULL` is a Phase 2 forward-only addition. The SQL source does not include it. It distinguishes a resident's self-proposed RT from a region confirmed by Village Admin, so RT/RW policies never expose an unverified self-selected region. It does not alter existing resident rows; those remain unverified until administratively reviewed.
- The source has nullable plaintext `birth_date` and `gender` columns. Phase 2 adds paired ciphertext/nonce/tag columns and encrypts existing non-null values before clearing those plaintext fields. The migration requires `DATA_ENCRYPTION_KEY` when existing demographic values are present; rollback decrypts them before removing the new columns. Never roll back on a shared or production database without an approved backup and key.
- The SQL `users.phone` field remains for schema compatibility, but Phase 2 adds ciphertext/nonce/tag columns and encrypts existing values before clearing it. The field is not currently used for SMS verification. Rollback decrypts it before removing the encrypted columns.
- The Laravel starter `users.name` column is absent from the SQL reference and may contain legacy personal names. Phase 2 preserves the required column for framework compatibility, encrypts every existing value into paired columns, and replaces the visible value with a non-personal `account-{id}` placeholder. Rollback decrypts it back; only use rollback on an approved disposable database or after an approved backup.

## Conflicts and decisions required

1. **Existing `users` schema:** the current Laravel migration creates required `name` and required unique `email`; the SQL defines required `username`, nullable unique `email`, optional `phone`, and `account_status`, but no `name`. Keep Laravel authentication/reset/session behavior compatible and do not store a duplicate plaintext full name. Migration history cannot be checked because no project database is configured/reachable. Use a forward-only migration unless a confirmed fresh disposable DB proves the historical migration has never been applied.
2. **Village Head role:** workflow and `letter_approvals.approval_level` require Village Head signing, but the SQL and project role list seed eight roles and omit Village Head. The user has confirmed Village Head as role 9; add the role to the idempotent seeder, and maintain the rule that Super Admin does not gain this authority automatically.
3. **Engine/runtime:** `.env` is absent, `.env.example` defaults to SQLite, no PDO drivers were loaded by the broken system PHP configuration, and no database server answered the local probe. Docker CLI exists but the current user cannot access its daemon socket. Do not run migrations until a dedicated MySQL 8 database is available and its version is verified.
4. **Input filename:** addendum refers to `integrated_village_platform_mysql8(2).sql`; the actual local file is `integrated_village_platform_mysql8.sql`. This map uses the latter, fully read file.
